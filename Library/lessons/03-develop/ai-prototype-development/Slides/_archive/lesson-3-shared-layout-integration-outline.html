The Shared Layout Pattern

Content Outline — What Students Learn

Part A: The Concept (Why This Pattern Exists)

What's shared vs. what changes

Every screen has a layout shell — header, footer, navigation, sidebar. Redesigning that shell means touching every screen file individually. This pattern puts the shell in one file, and all screens point to it.

The two versions of propagation

Built-in (GOV.UK Prototype Kit): Pages extend a layout; update it once and every page updates automatically.
Prompt-driven (your approach): One shared file that all pages reference; a controlled prompt handles the sync.

Why designers need this

You spot an issue with the header on screen 3. Rather than editing every screen individually (and risking drift), you fix the shared layout once and sync. One edit, one prompt, all screens consistent.

Part B: How It Works (The Implementation)

File structure

Keep shared layout separate from journey-specific content.

screens/
shared-layout.html ← Navigation, header, footer (the shell)
journey-a/
page-1.html (includes shared-layout)
page-2.html (includes shared-layout)
journey-b/
page-3.html (includes shared-layout)
page-4.html (includes shared-layout)
How pages reference it

Each page includes the shared layout as an HTML fragment or component. When the layout changes, pages don't need to be regenerated—they already point to the latest version.

When to sync

You edit shared-layout.html (e.g., change the header height, update navigation). Then you run the sync prompt once. Done.

Part C: The Sync Prompt

This is the prompt students use when they've changed shared-layout.html and need all journey pages to pick up the change:

"I've updated `screens/shared-layout.html`. All journey pages at `screens/journey-*/` reference it. Update each page to ensure the shared layout is correctly included and no conflicting styles override it. List every file you touched and what changed. If a page has diverged (custom styling in the header), report it—don't force it to match. Only update the layout inclusion—don't regenerate the page's main content."

Part D: Why This Matters (Designer POV)

Speed: Iteration gets faster

First journey took time to design and review. Second journey costs a fraction because the system (including layout) is locked. Changes to the layout are now one-file edits, not screen-by-screen.

Consistency: Drift prevention

Without a shared layout, screen-by-screen edits subtly diverge (one person uses 16px padding, another uses 18px). A single source of truth for the shell eliminates that.

Confidence: Visible proof the system works

Changing one file and watching three screens instantly reflect it is proof that your rules and templates are doing their job. It's not magic—it's structure.
